# KardsAFK4EXP 逻辑解读

> 面向"想看懂这堆代码到底在干嘛"的完整拆解。文中「原版第 N 行」均指上游 481 行的原始 `kards.py`；本仓库修复后的代码在 `kards.py`。

---

## 一、本质：它是什么层级的外挂

**结论：屏幕模板匹配 + 键鼠宏，不是游戏 AI。**

- **不**读游戏内存、**不**抓包改包、**不** hook 客户端、**不**注入 DLL。
- 全部"智能"来自 43 张 PNG 截图模板。代码做的事只有一个循环：**截图 → 在截图里找模板 → 找到就移动鼠标点它**。
- 因此它没有牌局理解：不认识费用、不认识卡牌效果、不认识场面优劣。它只会无脑把牌往敌方总部拖 + 点结束回合 + 4 分钟投降。

这种方案的好处是**几乎不可能被客户端反作弊检测**（对外部而言它和一个疯狂移动鼠标的玩家没有区别）；坏处是**极其脆弱**——游戏改一次 UI、改一次分辨率、换一张卡面，脚本立刻瞎掉。

依赖只有 5 个（`requirements.txt`）：`pyautogui / pyscreeze / opencv-python / numpy / pygetwindow`。其中 `opencv-python` 是 `confidence` 参数（模糊匹配）所必需的，`pygetwindow` 在原版里实际**全程被注释**、从未使用。

## 二、运行架构：一主一线

```
main()                                    ← 主线程，无限 while True
 └─ 每轮把"所有可能的按钮"都试一遍
      start_game_out() → daily_mission() → main_menu() → restart() → exit_game()
      → click_pass_button() → _handle_result_screens() → click_start_game_button()

surrender()                               ← 后台线程，点「确认」时启动
 └─ sleep(240) → 点投降 → 点二次确认 → 清除事件
```

关键设计：**主循环不是状态机，而是一个"扫描器"**。

它**不判断**"我现在处在哪个界面"，而是每个 tick 把所有已知按钮的模板都 `locateCenterOnScreen` 一遍，谁被找到了就点谁，全找不到就静默 `pass`。这是挂机脚本常见的新手写法——实现极简单，但代价是：

- 每轮要做十几次全屏/半屏截图，开销大、响应慢；
- 完全依赖"找不到图"来兜底，一旦某张模板在新界面里意外命中，就会误点。

`while not surrender_event.is_set()` 这层是"投降期间冻结主循环"的锁（原版是一个裸的全局 `bool`，见 CHANGELOG Bug#1）。

## 三、状态识别：靠 43 张截图当"传感器"

| 界面状态 | 识别模板 | 判定含义 |
|---|---|---|
| 官方启动器 | `start_gameOut.png` | 启动器上的「开始游戏」 |
| 主菜单 | `mainButton.png` / `clickedMainMenu.png` | 主菜单按钮 / 已选中态 |
| 对战选择 | `startBattle.png` / `friendsBattle.png` / `renj.png` | 开始匹配 / 好友对战 / **人机对战** |
| 匹配/出征确认 | `confirm.png` | 「出战」确认，**这一下之后就开始算 4 分钟** |
| 我方回合 | `endTurn.png` / `clickedEndTurn.png`（空过） | 我方可以行动 |
| 对手回合 | `opponent_turn_button.png` | 对手正在行动，干等 |
| 投降 | `surrender.png` → `surrender2.png` | 投降 → 二次确认 |
| 结算 | `continue.png` / `getReward.png` / `closeAd.png` / `leaveBattle.png` | 继续 / 领奖 / 关广告 / 离开战场回顾 |
| 断线 | `restart.png` / `clickedRestart.png` | 启动器上的「重连/重新开始」 |
| 场上单位 | `bomber.png` / `fighter.png` / `mortar.png` / `guard.png` | 轰炸机 / 战斗机 / 迫击炮 / 守护 |
| 敌方总部 | `enemy_headquarters.png` | 打脸目标 |

**"人机对战"（`renj.png`）是这套脚本能稳定挂机的核心**：它永远只打 AI，不排真人，所以不会因为坑队友被举报，也不会因为对面是人类而被针对。

还有一类"按下态变图"的技巧很有意思：`clickedstartBattle.png`、`clickedMainMenu.png`、`clickedRestart.png`、`clickedEndTurn.png` —— 同一个按钮在**被点击/被选中/被悬停**后外观会变，作者为每个状态都截了图。这既是"点到了"的确认，也是状态机的替代品。

## 四、逐函数拆解

### 1. `click_start_game_button()` — 开局流程

```
找到 mainButton.png（主菜单）或 friendsBattle.png  ──── 否则 return False
  ↓
找到 startBattle.png ──── 否则 return False
  ↓
点两下 startBattle.png → 再点两下 clickedstartBattle.png（按下态确认）
  ↓
循环（最长 120 秒）：
    若 startBattle/friendAccept 仍可见 → 说明还在选择界面，return False 重来
    找 renj.png（人机对战）→ 双击      ← 关键：永远打 AI
    找 confirm.png → 单击 → 启动 240 秒投降计时 → return True
```

### 2. `click_pass_button()` — 回合核心

```
找到 clickedEndTurn.png（"空过"按钮）
  ├─ 找到：play_cards() 出牌 → 双击空过 → 等对手回合结束
  └─ 没找到：退化成 click_end_turn_button()（结束回合）
```

`click_end_turn_button()` 逻辑同构，只是按钮换成了 `endTurn.png`。

"空过"和"结束回合"在 KARDS 里是两个不同按钮（空过 = 放弃本回合响应机会），作者优先点空过，因为这能更快推进对局。

### 3. `play_cards()` — 所谓"出牌 AI"

真实执行顺序（**注意它并不智能**）：

| 阶段 | 行为 | 真实效果 |
|---|---|---|
| ① | 在**我方支援阵线**找 `bomber.png` / `mortar.png` | 轰炸机 → 优先打敌方战斗机，没有就打总部；迫击炮 → 直接打总部 |
| ② | 确认 `pass/endTurn` 按钮存在（= 轮到我方响应） | 保证时序 |
| ③ | `for i in range(6)`：点 `(800+i*100, 屏幕高-100)` 然后拖向敌方总部 | **盲打手牌**，完全不看费用 |
| ④ | 再找战斗机 / 轰炸机，往敌方总部拖 | 补刀手牌阶段新出场的单位 |

**最关键的缺陷：它把"部署"和"攻击"混为一谈。**
在 KARDS 里，手牌里的单位卡必须拖到**自己的支援阵线**才会部署上场；拖到敌方总部通常是无效操作（或直接构成攻击指令而单位还没上场）。所以脚本"能把一局打完"，却几乎赢不了——不过它本来也不想赢。

**费用检测被整段注释了。** 作者其实已经把骨架写好了：

```python
def coast(x, y):                              # 按卡牌左上角相对位置算费用数字区域
    region_top = (x - 91, y - 206)
    region_bottom = (region_top[0] + 30, region_top[1] + 45)
    return (region_top[0], region_top[1], region_bottom[0], region_bottom[1])

coast_color_True = (232, 180, 78)             # 费用数字变色（= 打得起）的 RGB
```

配套的 `pyautogui.pixelMatchesColor(..., tolerance=10)` 循环在 4 处全被注释。也就是说：**"只打打得起的牌"这个能力，作者写完了但没启用**。这是整个仓库性价比最高的一个待办（见第七节）。

### 4. `surrender()` — 4 分钟策略

```
sleep(240) → 点 surrender.png → 等 0.5s → 点 surrender2.png
```

这是"防封"设计的核心：不挂满 20 分钟一局，而是每 4 分钟一局，模拟正常玩家节奏。README 里解释得很直白——**赢局超过 4 分钟经验不再增长**，所以 4 分钟就是单位时间的经验最优解。

> 但这套逻辑同时是 Bug#1 的温床：一旦投降失败，主循环就永久停摆。

### 5. `_handle_result_screens()` — 结算界面

优先级从高到低，找到哪个点哪个：`continue` → `getReward` → `closeAd` → `leaveBattle`。`checkBattle.png` 只做"把鼠标移过去"不点击，用来消除 tooltip 遮挡。每个循环都有 60 秒上限（原版是无上限的 `while`）。

## 五、坐标与时序常量

| 常量 | 值 | 语义 |
|---|---|---|
| `BOX_MINE` | `(501, 733, 1704, 988)` | 我方支援阵线，(x1,y1,x2,y2) |
| `BOX_ENEMY` | `(437, 150, 1760, 397)` | 敌方支援阵线 |
| `HAND_CARD_*` | `800 + i×100, H-100` | 手牌盲打位置 |
| 置信度 | 场上 0.90 / UI 0.70 | 模板匹配阈值 |
| 投降延迟 | 240s | 经验封顶时间 |
| 分辨率 | 2220×1271 | 全部坐标的基础 |

**坐标系语义**是原版最隐蔽的 bug：作者写的是「左上角 + 右下角」，但 `pyautogui` 的 `region` 要的是「左上角 + 宽高」。修复后由 `to_region()` 显式转换（推导过程见 CHANGELOG Bug#5）。

## 六、还能怎么改进（按性价比排序）

1. **恢复费用检测**（最高性价比）。骨架已现成，启用后至少不会去拖一张打不出的牌，`play_cards()` 的有效动作率会显著提升。
2. **区分部署与攻击**：手牌里的单位卡拖到 `BOX_MINE` 内，指令卡/攻击才拖向敌方目标。这一步做完，胜率会从"几乎为零"变成"能赢人机"。
3. **截图缓存**：一轮 tick 内所有识别共用**同一帧**。原版每调一次 `locate*` 就截一次全屏，一轮下来十几次截图，时间全浪费在这上面。用 `mss` 替换 `pyautogui.screenshot` 还能再快 5–10 倍。
4. **上状态机**（见下节），去掉"全按钮试探"。
5. **加守护单位识别**：`guard.png` 已经在仓库里，代码里被注释掉了。有守护在场时应当优先解守护，否则攻击会被强制转移。

## 七、若要真的会打牌：重构路线

现有架构撑不住"会打牌"，必须分层：

```
感知层   一次截图（mss）→ 缓存帧，所有识别基于同一帧
         模板匹配定位 → 结构化场面：
         手牌[N]{卡图, 费用, 是否打得起}, 我方阵线[X], 敌方阵线[Y], 敌方总部HP
            ↓
状态层   显式状态机：
         LAUNCHING → MENU → MATCHING → MULLIGAN → MY_TURN → OPP_TURN → RESULT
         每个状态独立超时 + fallback，而不是"全按钮都试一遍"
            ↓
决策层   规则引擎（费用判断 → 单位/指令区分 → 优先解场 → 再打脸）
         进阶：截图喂给视觉语言模型（VLM）直接输出动作
            ↓
执行层   拖动带缓动、失败重试、动作后校验（点完再截图确认状态真的变了）
```

其中**感知层**的关键是费用数字的 OCR/颜色判定（`coast()` 已经写了一半）和卡牌类型区分（单位 vs 指令，可看卡面图标）；**决策层**用纯规则就够打赢人机，不必上模型。

## 八、风险提示

- 这是**违反 KARDS 用户协议**的自动化脚本，账号有被封的真实风险。
- 上游 README 自称"稳定防封"，但同一份 README 又写"不排除 1939 破防直接封"——**后者才是实话**。降低频率、随机化时序只能降低被举报/被统计特征命中的概率，不能保证安全。
- 本仓库仅做缺陷修复与工程化整理，不构成任何使用建议。
